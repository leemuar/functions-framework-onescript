# functions-framework-onescript

Functions Framework для [OneScript](https://oscript.io).

Вы пишете обычный файл OneScript с одной экспортной процедурой, а фреймворк берёт на себя всё остальное:
поднимает HTTP-сервер, принимает запросы и вызывает вашу процедуру. Запускать функцию можно на своём
компьютере, в контейнере или в облаке, где есть serverless-контейнеры (например, Google Cloud Run или
Yandex Cloud Serverless Containers).

Фреймворк следует тому же контракту, что и [официальные реализации Google](https://github.com/GoogleCloudPlatform/functions-framework)
для Node.js, Python, Go, Java и других языков. Поэтому настройки (`--target`, `--source`,
`--signature-type`, `--port` и соответствующие переменные окружения) и поведение сервера вам, скорее всего,
уже знакомы.

## Что понадобится

OneScript версии **2.1.0 или новее**. Причин две:

- Встроенный веб-сервер (класс `ВебСервер`), на котором работает фреймворк, появился в OneScript только
  в версии 2.0.
- В версиях до 2.1.0 есть ошибка в чтении и записи JSON: если внутри объекта лежит строка с датой
  в формате ISO 8601, у которой доли секунды оканчиваются нулём (например, `2020-04-23T07:38:57.230Z`),
  то после чтения и обратной записи она превращается в `...57.23Z`. Для функций, работающих с
  CloudEvent, это означает незаметную порчу данных события.

Проверить версию можно командой `oscript --version`.

## Установка

Фреймворк опубликован в хабе пакетов OPM:

```bash
opm install functions-framework-onescript
```

Вместе с библиотекой в системе появляется команда `functions-framework`. По сути это короткая обёртка
над `oscript server.os`, поэтому дальше в примерах используется именно она.

Если не хочется ставить пакет в систему (или нет прав на запись в `/usr/local/bin`), его можно поставить
локально, в каталог `oscript_modules` текущей папки:

```bash
opm install -l functions-framework-onescript
./oscript_modules/bin/functions-framework --source my-function.os
```

Также можно просто склонировать репозиторий и запускать `oscript server.os` напрямую: всё, что
написано ниже про команду `functions-framework`, верно и для такого запуска.

## Быстрый старт

Создайте файл `main.os`:

```bsl
Процедура main( Запрос, Ответ ) Экспорт
	Ответ.Записать( "Привет из OneScript!" );
КонецПроцедуры
```

Запустите фреймворк в той же папке:

```bash
functions-framework
```

Вы увидите сообщение вида:

```
Starting functions framework server, port: 8080, function name: main, function signature type: http
```

В другом терминале отправьте запрос:

```bash
curl http://localhost:8080/
```

```
Привет из OneScript!
```

Что здесь произошло:

1. Фреймворк не получил ни одной настройки и взял значения по умолчанию: файл `main.os`, порт `8080`.
2. Он загрузил файл и нашёл в нём экспортную процедуру `main`. Если не указано иное, функция с таким
   именем считается HTTP-функцией.
3. На каждый запрос он вызывает `main`, передавая ей объекты запроса и ответа.

## HTTP-функции

HTTP-функция принимает два параметра: `Запрос` и `Ответ`. Их имена могут быть любыми, важен порядок.

Ниже примеры по нарастающей сложности. Каждый можно сохранить в отдельный файл и запустить командой
`functions-framework --source имя_файла.os`.

### Читаем параметры запроса

```bsl
Процедура main( Запрос, Ответ ) Экспорт

	Имя = Запрос.Параметры.Получить( "name" );
	Если Имя = Неопределено Тогда
		Имя = "мир";
	КонецЕсли;

	Ответ.Записать( "Привет, " + Имя + "! Метод: " + Запрос.Метод + ", путь: " + Запрос.Путь );

КонецПроцедуры
```

```bash
curl "http://localhost:8080/hi?name=Anna"
```

```
Привет, Anna! Метод: GET, путь: /hi
```

`Запрос.Параметры` содержит параметры строки запроса (после `?`), `Запрос.Метод` и `Запрос.Путь` — HTTP-метод
и путь. Остальные свойства запроса: `Заголовки`, `Тело`, `Куки`, `Хост`, `Схема`, `ТипКонтента`,
`ДлинаКонтента`, `Форма`.

### Отвечаем JSON

Если нужно вернуть структуру или соответствие в виде JSON, используйте `ЗаписатьКакJson`. Заголовок
`Content-Type: application/json` проставится сам.

```bsl
&HttpFunction
Процедура Статус( Запрос, Ответ ) Экспорт

	Результат = Новый Структура;
	Результат.Вставить( "message", "ok" );
	Результат.Вставить( "path", Запрос.Путь );

	Ответ.ЗаписатьКакJson( Результат );

КонецПроцедуры
```

Строка `&HttpFunction` над процедурой — аннотация. Она говорит фреймворку, что именно эту процедуру нужно
вызывать, и что это HTTP-функция. Благодаря аннотации процедуру можно назвать как угодно, а не только
`main`. Подробнее — в разделе [Как фреймворк выбирает функцию](#как-фреймворк-выбирает-функцию).

### Читаем тело запроса, задаём код и заголовки ответа

```bsl
&HttpFunction
Процедура Эхо( Запрос, Ответ ) Экспорт

	Если Запрос.Метод <> "POST" Тогда
		Ответ.КодСостояния = 405;
		Ответ.Заголовки.Добавить( "Allow", "POST" );
		Возврат;
	КонецЕсли;

	Чтение = Новый ЧтениеДанных( Запрос.Тело );
	Текст = ПолучитьСтрокуИзДвоичныхДанных( Чтение.Прочитать().ПолучитьДвоичныеДанные() );

	Ответ.КодСостояния = 200;
	Ответ.Заголовки.Добавить( "X-Echo", "yes" );
	Ответ.Записать( "Вы прислали: " + Текст );

КонецПроцедуры
```

```bash
curl -i -X POST -d "abc" http://localhost:8080/
```

```
HTTP/1.1 200 OK
X-Echo: yes

Вы прислали: abc
```

`Запрос.Тело` — это поток, поэтому его читают так же, как любой другой поток данных. Код ответа
задаётся через `Ответ.КодСостояния`, заголовки добавляются через `Ответ.Заголовки.Добавить`. Если код не
указан, сервер вернёт `200`.

### Что фреймворк делает сам

- Запросы к `/robots.txt` и `/favicon.ico` фреймворк отклоняет с кодом `404`, не вызывая вашу функцию.
  Так требует контракт Functions Framework: браузеры и поисковые роботы постоянно запрашивают эти
  адреса, и функции не нужно обрабатывать лишний шум.
- Если ваша функция выбросила исключение, клиент получит `500`, а в консоль будет выведено сообщение
  `Error during function execution: ...` с описанием ошибки.

## Функции для CloudEvent

[CloudEvents](https://cloudevents.io) — стандартный формат описания событий. Если ваша функция должна
реагировать на события (например, пришедшие из Eventarc, Knative или другого брокера), используйте
сигнатуру `cloudevent`. Такая функция принимает один параметр — событие:

```bsl
&CloudEventFunction
Процедура ПриСобытии( Событие ) Экспорт
	Сообщить( "Получено событие " + Событие["type"] + " от " + Событие["source"] );
	Сообщить( "Данные: " + Событие["data"]["name"] );
КонецПроцедуры
```

`Событие` — это соответствие (`Соответствие`) с атрибутами CloudEvent: `specversion`, `type`, `source`,
`id`, `time`, `subject`, `datacontenttype` и `data` (если они присутствуют в событии). Данные события лежат
в `Событие["data"]`.

Запустите функцию и отправьте событие. Фреймворк понимает оба режима передачи CloudEvent по HTTP.

**Structured** — всё событие передаётся в теле запроса в формате JSON:

```bash
curl -i -X POST http://localhost:8080/ \
  -H "Content-Type: application/cloudevents+json" \
  -d '{"specversion":"1.0","type":"com.example.greet","source":"/demo","id":"1","data":{"name":"Anna"}}'
```

**Binary** — атрибуты событий передаются в заголовках `Ce-*`, а в теле лежат только данные:

```bash
curl -i -X POST http://localhost:8080/ \
  -H "Ce-Specversion: 1.0" \
  -H "Ce-Type: com.example.greet" \
  -H "Ce-Source: /demo" \
  -H "Ce-Id: 2" \
  -H "Content-Type: application/json" \
  -d '{"name":"Boris"}'
```

В обоих случаях в консоли сервера появятся строки:

```
Получено событие com.example.greet от /demo
Данные: Anna
```

Ответы фреймворка:

| Ситуация | Код ответа |
|---|---|
| Функция отработала без ошибок | `204` (без тела) |
| Не удалось разобрать запрос как CloudEvent | `400` |
| Функция выбросила исключение | `500` |

## Как фреймворк выбирает функцию

В файле может быть много экспортных процедур. Чтобы понять, какую вызывать, фреймворк проверяет три
способа по очереди и останавливается на первом сработавшем:

1. **Аннотация.** Если экспортная процедура помечена `&HttpFunction` или `&CloudEventFunction`, будет
   выбрана она, а тип сигнатуры определится по аннотации. В файле должна быть только одна
   аннотированная процедура, иначе фреймворк остановится с ошибкой.
2. **Настройка `--target`** (или переменная `FUNCTION_TARGET`). Фреймворк вызовет экспортную процедуру
   с этим именем. Тип сигнатуры берётся из `--signature-type` (по умолчанию `http`).
3. **Процедура `main`.** Если ничего из перечисленного не нашлось, но в файле есть экспортная
   процедура `main`, будет вызвана она как HTTP-функция.

Например, в файле без аннотаций можно выбрать нужную процедуру явно:

```bash
functions-framework --source utils.os --target Обработать
```

А для функции CloudEvent без аннотации нужно дополнительно указать тип:

```bash
functions-framework --source events.os --target ПриСобытии --signature-type cloudevent
```

Если нужной процедуры в файле нет, фреймворк сообщит об этом и завершит работу.

## Настройки запуска

Любую настройку можно передать флагом командной строки или переменной окружения. Если указаны оба
варианта, побеждает флаг.

| Флаг | Переменная окружения | По умолчанию | Что делает |
|---|---|---|---|
| `--source` | `FUNCTION_SOURCE` | `main.os` | Файл со сценарием, в котором лежит функция |
| `--target` | `FUNCTION_TARGET` | не задано | Имя экспортной процедуры (см. выше) |
| `--signature-type` | `FUNCTION_SIGNATURE_TYPE` | `http` | Тип функции: `http` или `cloudevent` |
| `--port` | `PORT` | `8080` | Порт, на котором слушает сервер |

Примеры:

```bash
# другой файл и порт
functions-framework --source my-function.os --port 3000

# то же самое через окружение
FUNCTION_SOURCE=my-function.os PORT=3000 functions-framework
```

Значение флага нужно указывать отдельным аргументом после имени флага: `--port 3000`. Запись
через знак равенства (`--port=3000`) не поддерживается и не вызывает ошибки: флаг просто игнорируется,
и сервер запустится на порту по умолчанию.

## Запуск в облаке

Serverless-контейнеры (Google Cloud Run, Yandex Cloud Serverless Containers и подобные) предъявляют
к приложению два требования: оно должно слушать HTTP-порт, номер которого передаётся в переменной
окружения `PORT`, и принимать соединения на всех сетевых интерфейсах, а не только на `localhost`.

Фреймворк этим требованиям уже соответствует: порт он читает из `PORT`, а встроенный сервер слушает все
интерфейсы (в журнале при запуске это видно по строке `Now listening on: http://[::]:8080`). Значит,
чтобы запустить функцию в облаке, достаточно собрать образ, в котором установлен OneScript 2.1.0 или
новее и пакет `functions-framework-onescript`, и указать в качестве команды запуска
`functions-framework --source ваш-файл.os`. Все остальные настройки платформа передаст сама.

Готового Dockerfile в репозитории пока нет.

## Что делать, если что-то пошло не так

Фреймворк проверяет настройки при запуске и при ошибке завершается с понятным сообщением:

| Сообщение | Причина |
|---|---|
| `File not found: ...` | Файл из `--source` не существует (или в текущей папке нет `main.os`) |
| `Function with name ... specified in configuration not found in script file` | В файле нет экспортной процедуры с именем из `--target` |
| `Failed to determine the name of the function to execute` | Нет аннотации, не задан `--target` и нет процедуры `main` |
| `Multiple functions found to run, it is unclear which one to execute` | В файле несколько аннотированных процедур |
| `The function has multiple different annotations, which is not allowed` | У одной процедуры несколько разных аннотаций |
| `Invalid signature-type value: ...` | Недопустимое значение `--signature-type` |
| `Specified value ... is not a valid port number` | В `--port` или `PORT` указано не число |
| `The value of the command line parameter ... is not specified` | Флаг указан в конце команды без значения |

Обратите внимание: процедура должна быть **экспортной** (с ключевым словом `Экспорт`), иначе фреймворк её
не увидит.

## Проверка на соответствие контракту

Корректность работы проверяется официальным тестовым клиентом
[functions-framework-conformance](https://github.com/GoogleCloudPlatform/functions-framework-conformance).
В репозитории есть два минимальных сценария для него: [conformance-http.os](conformance-http.os)
и [conformance-cloudevent.os](conformance-cloudevent.os). Клиент собирается из исходников (на Go) и
запускается так:

```bash
client -type=http -buildpacks=false \
  -cmd="oscript server.os --source conformance-http.os"

client -type=cloudevent -validate-mapping=false -buildpacks=false \
  -cmd="oscript server.os --source conformance-cloudevent.os"
```

Флаг `-validate-mapping=false` нужен, потому что конвертация событий старого формата Google Cloud
в CloudEvent и обратно пока не реализована (см. следующий раздел).

## Чего пока нет

- **Legacy-события Google Cloud** (старый формат фоновых функций, `data` + `context`) и их конвертация
  в CloudEvent. Тип сигнатуры `event` не поддерживается.
- **Typed-функции** (тип сигнатуры `typed` в других реализациях).
- Настройка адреса, на котором слушает сервер: встроенный веб-сервер OneScript не позволяет её задать.
- Готовый Dockerfile и инструкции по развёртыванию в конкретных облаках.
